# 단계별 브랜치·전달·수신 확인·보고 절차

## 1. 브랜치의 목적

| 브랜치 | 목적 | 규칙 |
|---|---|---|
| `main` | 팀의 공통 기준·최종 확인본 | 기능은 S5 확인 후 반영. 사용자 승인된 문서·데이터 정비는 별개 |
| `integration` | 단계별 확인 결과를 모으는 공유 브랜치 | 각 단계 PR의 대상. 이 브랜치에서 직접 기능 개발하지 않음 |
| `feature/a-*`, `feature/b-*`, `feature/c-*` | 각자의 실제 작업 | 기존 작업·기여 이력 유지 |
| `handoff/sN-보내는역할-to-받는역할-vN` | 검사한 결과를 상대에게 넘기는 전달본 | 준비된 커밋에서 생성·push, 전체 SHA 고정. 후속 변경은 새 SHA·재확인 |
| `review/sN-받는역할-vN` | 수신자가 자기 작업과 전달본을 합쳐 확인 | 수신자의 작업 HEAD에서 생성해 전달 SHA를 merge. 사용자 변경 보존 |

전달 브랜치는 해당 단계에 필요한 준비된 커밋을 담는다. 전체 저장소를 복사하거나 완료되지 않은 다른 작업을 일괄 넘기지 않는다. 빈 전달 브랜치·PR을 미리 만들어 기능 준비 완료처럼 표시하지 않는다.

`integration`은 최초 준비 시 공통 기준 커밋에서 한 번 생성한다. 이미 존재하면 초기화하거나 강제 이동하지 않는다. 매 단계 시작 시 `origin/integration`을 fetch하고 실제 작업 브랜치에 필요한 기준을 정상 merge한다. 기존 사용자 변경이 있으면 먼저 보존 상태를 확인하며 강제 reset·일괄 덮어쓰기를 하지 않는다.

## 2. 단계와 수용 기준

| 단계 | 전달·통합 책임 | 준비된 결과 | 받는 사람이 확인할 것 |
|---|---|---|---|
| **S0 계약** | B API/환경·C 분석/차트, A 화면 확인 | G01~G03 계약·예제·버전·실행 전제 | 필드·단위·기간·NULL·오류 예제가 각 역할에서 같은 의미인가 |
| **S1 Bronze** | B·C | 확보한 원본·해시·진단·Delta 저장/조회 근거 | 최초 오염 원본과 C 입력 구분, 원본 값·행 보존, 버전·미확보 항목 |
| **S2 Silver** | B ↔ C | 제공 17테이블 기반 저장·사전·모델·검사 | 371,437행 기준·키·단위·기간·검토 상태, SQL/Pandas 대조 |
| **S3 Gold** | C → B, A 차트 의미 확인 | 보고서/일별 계산·계약·예제·검사, B 저장·실행 | 320/17,440행 기준, 공시시점·윈도·분모·수급·이중 합산·값 일치 |
| **S4 API→화면** | B → A, C 수치 확인 | 실제 API·샘플·실행법·환경·검사·다운로드 | A의 기존 화면과 실제 API 연결, 필터·NULL·기간·큰 금액·출처·오류 |
| **S5 전체** | A·B·C | 확인된 화면·서버·계산·증빙·재현 명령 | 동일 기업·기간의 원본→Gold→DB→API→화면·CSV, 잔여 이슈·F01~F08 |

단계는 수용 검사의 경계이며 전체 개발을 순차 대기로 묶지 않는다. S0의 제안 예제로 A 화면·B 저장·C 계산을 병렬 개발할 수 있다. S1 원본 미확보는 S2/S3의 제공 CSV 기반 개발을 막지 않는다. 단, 부분 결과를 Bronze→Silver 전체 재현 완료로 표시하지 않는다.

## 3. 전달자가 할 일

1. 본인 작업 브랜치·HEAD·미커밋 변경을 확인하고 관련 코드·검사·문서를 준비한다.
2. 해당 단계 범위와 필요한 선행 커밋만 포함되는지 diff를 확인한다.
3. 실제 검사한 커밋에서 전달 브랜치를 생성한다. 예: `handoff/s4-b-to-a-v1`.
4. 전달 브랜치를 원격에 push하고 **base=`integration`**인 PR을 만든다. 로컬 branch만 만들고 수신자에게 받으라고 하지 않는다.
5. [전달 양식](handoffs/TEMPLATE.md)을 단계별 기록으로 작성하고 [진행표](integration-status.md)에 브랜치·고정 SHA·PR·기록 링크를 남긴다. 전달 SHA는 문서 추가 이후에도 최종 검사 대상과 일치시킨다.
6. 실제 실행 명령·설치·환경·샘플 요청/응답·기대값·미실행·미확보를 제공한다. 실행하지 않은 서비스를 사용할 수 있다고 주장하지 않는다.
7. 수신자가 확인할 때까지 기능 완료/최종 병합으로 표시하지 않는다. 수정했다면 새 SHA·diff·검사 결과를 등록하고 재확인을 받는다.

위는 역할 개발 작업에서 사용할 절차다. 실제 push·PR은 해당 작업의 사용자 지시 범위 안에서 수행하며, 권한이 없으면 로컬 준비 상태와 아직 원격 전달되지 않았음을 보고한다. 임의로 상대 이름의 작업을 실행하거나 별도 메신저에 통보하지 않는다.

## 4. 수신자가 할 일 — B 결과를 A 작업에 합치는 예

**B:** B의 검사된 API 커밋을 `handoff/s4-b-to-a-v1`에 올리고 `integration` 대상 PR과 [S4 기록](handoffs/S4-B-to-A.md)을 남긴다.

**A:** 미커밋 작업·현재 브랜치를 먼저 확인한다. 작업이 안전하게 보존된 후 **현재 A 작업 HEAD에서** `review/s4-a-v1`을 만들고, B 기록의 전체 SHA가 원격 전달 브랜치에 실제 존재하는지 확인해 해당 SHA를 merge한다. B 브랜치로 이동해서 A의 화면 작업이 빠진 상태를 검사하지 않는다.

```text
A의 feature/a-* HEAD ──→ review/s4-a-v1 ──→ 실제 화면/API 검사
                                      ↗
B의 handoff/s4-b-to-a-v1 고정 SHA ──────┘
```

A는 API 실행·환경부터 확인하고 필터·정상·NULL·빈 결과·오류·다운로드를 화면에서 검사한다. B와 A 양쪽 커밋, 검사 명령·브라우저 결과·미해결을 기록한다. 계약 판단이 필요한 충돌은 관련 파일·선택지·영향을 구체적으로 보고하고, 단순 중복은 같은 변경 여부를 확인해 해결한다.

A가 수정할 화면 연결 코드는 A 소유 커밋으로 남긴다. B의 API PR에 무관한 A 작업 전체를 섞지 않는다. 확인 브랜치는 `main`으로 바로 밀지 않고 B 전달 PR 검증 증거로 사용한다. A의 화면 변경은 별도 전달 PR로 S5 통합에 포함한다. C→B의 S3도 같은 방식으로 B의 기존 작업 HEAD에서 C 결과를 합쳐 실행 확인한다.

## 5. 병합·보고

- 수신 확인 후 해당 역할의 PR을 `integration`에 정상 병합한다. 원래 커밋·기여를 보존할 수 있는 merge 방식을 사용하고 공유 이력을 강제 재작성하지 않는다.
- 다른 역할의 로컬 작업을 자동 갱신했다고 가정하지 않는다. 병합 SHA를 진행표에 남기고 각자 fetch 후 실제 작업 브랜치에 반영한다. 같은 커밋을 다시 cherry-pick하지 않는다.
- 모든 단계의 기능을 다시 순서대로 병합하는 것이 아니라 **아직 포함되지 않은 준비 커밋과 의존성**만 확인해 반영한다.
- S5에서 공동 통합을 검사한 뒤 최종 `integration`→`main` PR을 준비한다. 수신 확인은 상대 역할의 검사이며 사용자 승인이나 최종 병합과 구분한다.
- 보고서는 `단계 / 전달자→수신자 / 전달 브랜치·SHA·PR / 수신 확인 브랜치·SHA / 실행법 / 실제 검사·결과 / 병합 SHA / 남은 일`로 작성한다.

## 6. 수신자가 에이전트에 한 번에 전달할 문장

```text
Team-Zero의 AGENTS.md와 docs/integration-workflow.md, docs/integration-status.md 및 해당 단계 전달 기록을 읽어 줘. 내 기존 작업·미커밋 변경을 보존하고 기록된 원격 전달 브랜치와 고정 SHA·PR 상태를 확인해 줘. 준비된 전달본이면 내 작업 HEAD에서 별도 review 브랜치를 만들어 해당 SHA를 합치고, 전달된 실제 실행법과 담당 수용 검사를 수행해 줘. 없는 입력·미해결 계약은 구체적으로 보고하면서 가능한 검사는 계속하고, 단계 기록에 결과·충돌·남은 작업을 남겨 줘. 원격 push·PR 병합·main 반영은 이 요청에 포함하지 않아.
```
